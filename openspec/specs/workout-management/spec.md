# 运动管理规格

## Purpose

定义运动浏览搜索、会话生命周期、手动录入、计划与推荐内容行为。

## Requirements

### Requirement: 浏览与搜索运动

系统 MUST 以多彩分类卡展示跑步、步行、骑行、力量、瑜伽和 HIIT，允许按名称搜索，并从分类进入细分训练方案列表。

#### Scenario: 搜索匹配内容
- **WHEN** 用户输入运动名称、方案名称或分类关键词
- **THEN** 系统实时展示匹配分类和方案，并在无结果时展示可恢复空状态

#### Scenario: 用户尚无运动记录
- **WHEN** 本地 Core Data 中没有用户创建或完成的运动
- **THEN** 历史页展示真实空状态，不显示伪造运动和示例路线

#### Scenario: 打开跑步分类
- **WHEN** 用户点击跑步分类
- **THEN** 系统展示五公里、减脂跑、间歇冲刺等方案及其难度、时长和目标

### Requirement: 运动会话生命周期

系统 MUST 支持准备、开始、暂停、继续、结束和保存运动会话，并防止非法状态转换和重复保存；户外跑步、步行和骑行 SHALL 在获得使用期间定位权限后记录真实路线与累计距离。

#### Scenario: 完成户外跑步
- **WHEN** 用户授权定位后开始跑步、暂停后继续并最终结束
- **THEN** 系统过滤低质量定位点，保存唯一运动记录及真实时长、累计距离和可用路线摘要

#### Scenario: 会话保存失败
- **WHEN** 结束运动时持久化失败
- **THEN** 系统保留可恢复会话并允许用户重试，不得静默丢失记录

#### Scenario: 定位不可用
- **WHEN** 用户未授权定位、设备没有有效点位或定位在运动中断
- **THEN** 系统继续记录真实时长并允许完成运动，距离和路线保持不可用且不使用示例数据

### Requirement: 手动添加运动

系统 MUST 允许用户填写运动类型、开始时间、时长、距离和热量，其中运动类型与时长为必填项。

#### Scenario: 提交有效手动记录
- **WHEN** 用户提交字段合法的手动运动
- **THEN** 系统保存记录并使其立即出现在历史列表

#### Scenario: 提交缺失信息
- **WHEN** 用户未填写运动类型或有效时长
- **THEN** 系统阻止保存并在对应字段显示中文错误提示

### Requirement: 运动计划与推荐

系统 SHALL 展示快速开始、推荐训练、训练目标、难度、预计时长、安全提示和开始入口；已发布的远程计划优先展示并明确标识来源与语言，本地降级内容必须标明为本地内容，远程内容未配置、无发布数据或不可达时不得显示为已同步。

#### Scenario: 查看推荐训练
- **WHEN** 用户进入运动 Tab 并打开任一推荐方案
- **THEN** 系统展示完整讲解、阶段安排、注意事项和适用的开始运动入口

#### Scenario: 服务端方案可用
- **WHEN** 服务端返回有效已发布训练方案
- **THEN** 运动页展示服务端方案，并标识为远程已发布内容

#### Scenario: 服务端无发布方案
- **WHEN** 服务端返回有效空目录
- **THEN** 运动页展示真实空状态，不以本地示例填充

#### Scenario: 服务端不可达
- **WHEN** 服务端训练目录请求失败
- **THEN** 运动页可以展示内置方案，但必须标识本地降级并提供重试

### Requirement: 动作库入口

系统 MUST 从运动页提供动作库入口，并通过动作目录协议展示本地基础内容或远程数据状态。

#### Scenario: 打开动作库
- **WHEN** 用户点击动作库入口
- **THEN** 系统展示可搜索动作列表、过滤条件和服务端数据状态

### Requirement: 服务端运动记录同步

系统 MUST 在恢复有效会话后分页读取服务端运动记录，并与 Core Data 和 HealthKit 记录按稳定标识及来源合并，不得遗漏后续游标页面或重复展示同一条记录。

#### Scenario: 读取多页运动历史
- **WHEN** 服务端运动列表返回下一页游标
- **THEN** 系统继续请求直至游标为空，并一次性发布合并后的历史状态

#### Scenario: 历史服务不可达
- **WHEN** 服务端运动请求失败
- **THEN** 系统仍展示 Core Data 与 HealthKit 记录，并明确远程历史未加载

### Requirement: 本地优先上传运动记录

系统 MUST 先保存用户在 MoveFit 完成或手动添加的运动，再为主后端支持的运动类型创建服务端记录；远程失败不得回滚或丢失本地记录。

#### Scenario: 保存受支持运动
- **WHEN** 已登录用户完成 running、walking、cycling、yoga、strength 或 hiit 运动
- **THEN** 系统使用稳定运动 ID 和幂等键创建服务端记录，并在成功后标记已同步

#### Scenario: 保存后端未支持的运动类型
- **WHEN** 用户保存拉伸等当前后端枚举不支持的运动
- **THEN** 系统保留本地记录并显示“当前服务端不支持该类型”，不得发送伪造类型

#### Scenario: 设备健康记录存在
- **WHEN** HealthKit 返回设备运动样本
- **THEN** 系统展示真实设备数据，但未经明确上传策略不得自动批量写入服务端

### Requirement: 动作双帧媒体展示

系统 MUST 按动作服务 `images` 的顺序展示可用图片：第一张标记为起始动作，第二张标记为结束动作；动作说明在图片缺失、加载失败或仅有一张图片时仍必须可读。

#### Scenario: 远程动作含两张图片
- **WHEN** 用户打开含两张远程图片的动作详情
- **THEN** 系统展示可切换的起始与结束图片及对应无障碍标签

#### Scenario: 图片不完整
- **WHEN** 动作没有图片、仅有一张图片或图片下载失败
- **THEN** 系统显示明确的媒体不可用状态且不隐藏步骤和安全说明

### Requirement: 运动发现视觉层级

系统 MUST 将运动页面组织为快速开始、训练推荐、运动类别和动作库入口，并让类别和训练封面使用可区分但可读的视觉语言。

#### Scenario: 用户浏览运动 Tab
- **WHEN** 用户进入运动 Tab
- **THEN** 用户能优先看到开始运动和推荐训练入口，并可继续进入分类与动作库
